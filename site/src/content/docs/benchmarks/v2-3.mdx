## Task-accuracy evaluation

<Aside type="tip" title="Summary">
  - On specs over 1 MB, routed slices used `45.4×` fewer Claude input tokens than the raw spec and scored `19 / 19` against raw's `18 / 19`. Both sides uncached, routing cost `187×` less.
  - A cached raw spec still cost `29.7×` more than a cached routed run, and `9.8×` more than an uncached routed run.
  - On specs under 30 KB, the raw spec is still the better choice. It used `2.3×` fewer tokens, cost `2.3×` less and scored `28 / 28`.
  - Both 7.9 MB Stripe tasks failed raw with `Prompt is too long`. Routed scored `8 / 8`.
</Aside>

The method is the same as for 2.2.0. Eleven contract tasks ran serially on `claude-haiku-5-5` through `claude -p`, with no tools and an isolated system prompt. Each cell got `3` graded trials, and the large raw specs got `1`. Deterministic JSON assertions graded every trial (`55` in total), with no LLM judge.

The six conditions are:

1. `no_spec`: the question alone, as a memorization control.
2. `summary`: `vimanam --detail summary --no-report`.
3. `routed_e2e`, the real workflow:
   - Turn 1 reads the summary and picks `--operation-id` or `--operation`, plus up to `3` `--schema` names.
   - The harness runs `vimanam` with `--schema-depth 2` on every call.
   - Turn 2 either answers or asks for up to `3` more schemas with `{"fetch_schemas": [...]}`, and Turn 3 answers.
   - Totals add up every turn's tokens, cost and latency.
4. `fixed_slice`: one `--operation … --detail full --include-schemas --schema-depth 2` call, a deliberately naive single-turn baseline.
5. `oracle_slice`: the same slice plus `--schema` (depth 2) for exactly the types that hold the answers. The harness refuses to run unless every answer marker is in this slice.
6. `raw_spec`: raw YAML, JSON, concatenated `.proto` files, or `.graphql` SDL.

Comparing `routed_e2e` with `oracle_slice` measures routing quality. Comparing `oracle_slice` with `raw_spec` measures how readable the slice is.

Every graded trial prepends a fresh nonce to each prompt, so every graded call is a cold-cache call. Right after trial 1, the harness replays its exact prompts with the same nonce to measure the warm-cache cost. The replay isn't graded.

The tasks are:

- `pb_ledger_stream`, `pb_fleet_dispatch` and `pb_vault_audit`: synthetic multi-file `.proto` services, so memorization can't help.
- `pb_otel_trace_export`: the real OpenTelemetry `TraceService.Export`, whose answers sit beyond depth 2.
- Public OpenAPI and GraphQL specs pinned to fixed commits for the other seven tasks.

Size classes use the raw spec size:

- Large: over 1 MB and fits in context (OpenAI ×3, GitHub `createIssue`).
- Small: under 30 KB (the four protos and SpaceX).
- Too large: the two 7.9 MB Stripe tasks.

### Findings

1. Routing picked the right target every time. Turn 1 chose the expected operation, and `vimanam` exited `0`, in all `33 / 33` routed trials.
2. The follow-up path runs when it's needed and not otherwise:
   - On the three tasks whose answers sit beyond depth 2 (`pb_fleet_dispatch`, `pb_vault_audit` and `pb_otel_trace_export`), the model called `fetch_schemas` in `9 / 9` trials.
   - It asked for no follow-up in any of the other `24` trials.
3. The `request.` prefix is gone from answers. In 2.2.0, `5` routed trials answered with field names such as `request.input_file_id`, which only a prefix-tolerant grader accepted. In 2.3.0, body tables list real field paths ([#156](https://github.com/noemaforge/vimanam/issues/156)), and no trial in any condition used the prefix.
4. `fixed_slice` now answers both GraphQL tasks. It scored `5/5` on `gql_spacex_launches` and `gql_github_create_issue`, against `2/5` each in 2.2.0. Operation slices now include argument input types such as `CreateIssueInput` ([#170](https://github.com/noemaforge/vimanam/issues/170)).
5. `fixed_slice` still fails the depth-limited proto tasks (`0/5`, `0/6` and `2/6`), because their answers sit beyond depth 2. Use `oracle_slice` to judge slice readability: it scored `54 / 55`, and its only misses were the answer format.
6. The crossover is still around tens of kilobytes. Below 30 KB, routing takes 2 to 3 sequential turns (`23.8 s` of API latency across the five small tasks) against `9.2 s` for raw. Above 1 MB, routing costs less at the same or better accuracy, but took `18.3 s` against raw's `10.1 s`.

### Compared with the 2.2.0 run

The two runs are comparable. They use the same 11 tasks, assertions and corpus files (the SHA-256 hashes in `meta.corpus_sha256` match). Both runs used the `haiku` alias, which resolved to `claude-haiku-5-5`, with `3` trials and `--workers 1`.

Two things changed in the method:

- The Claude Code CLI moved from `2.1.319` to `2.1.332`. Each call now sends about `400` more input tokens: `no_spec`, which sends only the question, rose from `17,132` to `21,630` tokens across 11 tasks.
- The harness makes one short preflight call before any trial and stops if it fails. That call isn't graded or counted.

Because of the CLI overhead, token and cost totals rise in every condition, including `no_spec`. Compare ratios and scores rather than absolute token counts.

| Measure | 2.2.0 | 2.3.0 |
|---|---:|---:|
| `routed_e2e` assertions, all 11 tasks | `55 / 55` | `54.67 / 55` |
| `routed_e2e` trials using the `request.` prefix | `5` | `0` |
| `fixed_slice` assertions, all 11 tasks | `31 / 55` | `38.66 / 55` |
| `oracle_slice` assertions, all 11 tasks | `53 / 55` | `54 / 55` |
| `raw_spec` assertions, all 11 tasks | `47 / 55` | `46 / 55` |
| `no_spec` assertions, all 11 tasks | `0 / 55` | `4 / 55` |
| `routed_e2e` tokens, large tasks | `32,077` | `37,602` |
| Raw over routed tokens, large tasks | `53.1×` | `45.36×` |
| Raw over routed cost, cold, large tasks | `208×` | `186.87×` |
| Raw over routed cost, warm, large tasks | `33.2×` | `29.71×` |

About `3,300` of the `5,525`-token rise in large routed tokens is the CLI overhead: 4 tasks × 2 turns × about `408` tokens. The rest comes from larger 2.3.0 slices, such as `oa_batches` going from `7,768` to `9,716` tokens.

## Tokenizer calibration: Claude API tokens vs `o200k_base` vs `chars / 4`

Vimanam's `--max-tokens`, `--stats` and `--costs` estimate tokens as `chars / 4` (`estimate_tokens` in `src/markdown/mod.rs`). The eval measures net Claude input tokens on `claude-haiku-5-5` (median input tokens minus the `no_spec` baseline) for payloads of at least 1,000 characters. Subtracting the baseline removes the CLI overhead from these figures.

| Content format | Samples | Median chars / `o200k_base` token | Median chars / Claude token | Median Claude / `o200k_base` |
|---|---:|---:|---:|---:|
| Vimanam Markdown | `28` | `3.83` | `2.26` | `1.61×` |
| GraphQL SDL | `2` | `3.83` | `2.38` | `1.60×` |
| Protobuf / gRPC | `4` | `4.22` | `2.27` | `1.86×` |
| OpenAPI YAML | `3` | `4.89` | `3.38` | `1.45×` |

On Vimanam Markdown, `chars / 4` undercounts Claude tokens by about `1.77×` (`4 / 2.26`). `--max-tokens 1600` therefore allows about `2,800` Claude tokens ([#165](https://github.com/noemaforge/vimanam/issues/165)).

## Limits in v2.3.0

<Aside type="caution" title="Measured limits and open issues">
  - `chars / 4` undercounts Claude tokens by about `1.77×` on Vimanam Markdown ([#165](https://github.com/noemaforge/vimanam/issues/165)).
  - Single-turn depth-2 slices miss answers that sit deeper, as `fixed_slice` shows on the three proto tasks. Use the follow-up turn or name the deeper types with `--schema`.
  - Below about 30 KB, the raw spec costs less and answers faster than routing.
  - These results cover one Claude model and 11 tasks. Two of the OpenTelemetry task's three `no_spec` trials scored `6/6` from memory.
</Aside>
