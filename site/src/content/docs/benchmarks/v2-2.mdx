## Task-accuracy evaluation: end-to-end routed workflow vs fixed slice vs raw spec

Extracting one operation out of 612 is selection, not compression. To measure whether an LLM using Vimanam answers exact contract questions accurately without oracle hints or training-data memorization, ten contract tasks ran serially (`--workers 1`) under five conditions on `claude-haiku-5-5` (zero tools, isolated system prompt, `3` trials per cell; `1` trial on >100k-token `raw_spec`):

1. **`no_spec`** *(memorization control, 3 trials/task)*: question only, no contract context.
2. **`summary`** *(3 trials/task)*: `vimanam --detail summary --no-report`.
3. **`routed_e2e`** *(real workflow, 3 trials/task)*: Turn 1 reads `vimanam --detail summary` and chooses `--operation-id` / `--operation` and optional `--schema` names. The harness runs `vimanam` with a uniform `--schema-depth 2` on **both** operation and `--schema` calls. Turn 2 answers from the retrieved slice or returns `{"fetch_schemas": [...]}` for one follow-up `--schema ... --schema-depth 2` call before answering on Turn 3. Totals sum **all turns' Claude API input tokens, wall latency, and USD cost**.
4. **`fixed_slice`** *(3 trials/task)*: uniform single-turn `vimanam --operation ... --detail full --include-schemas --schema-depth 2 --no-report` with no extra `--schema` flags (not an oracle upper bound).
5. **`raw_spec`** *(3 trials on small specs; 1 trial on >100k-token specs)*: raw YAML, raw JSON, concatenated `.proto` + transitive imports, or raw `.graphql` SDL — executed on all 10 tasks, including both Stripe `7.9 MB` JSON tasks, which returned `exit 1`, `"terminal_reason": "blocking_limit"`, and `"Prompt is too long"`.

The three Protobuf tasks use checked-in synthetic multi-file services (`ledger/v1`, `fleet/v2`, and `vault/v1` in [`scripts/eval-fixtures/protos/`](https://github.com/noemaforge/vimanam/tree/main/scripts/eval-fixtures/protos)) so public-spec memorization cannot inflate `no_spec` or `summary`, and `fleet/v2` + `vault/v1` place requested sub-messages beyond depth 2 to actively exercise the Turn-3 `fetch_schemas` follow-up path.

Every response was graded deterministically on strict JSON assertions (`49` assertions across `10` tasks; `138` total serial trials; no LLM judge).

### Key findings from the serial evaluation

1. **Zero memorization contamination and verified target routing (`30 / 30`)**: `no_spec` scored `0 / 49` (`0.0%`) across all 30 control trials. In `routed_e2e`, Turn 1 selected the **exact expected target operation** (`route_target_matched = 1.0`) and exited `0` (`routed_cmd_ok = 1.0`) in **`30 / 30` trials**.
2. **Turn-3 `fetch_schemas` follow-up loop works end to end (`6 / 6` on depth-3 tasks, `0 / 24` spurious)**: on `pb_fleet_dispatch` and `pb_vault_audit`, single-turn `fixed_slice` at `--schema-depth 2` scored `2/6` and `0/5` because `fleet.v2.AssignmentOutcome`, `vault.v1.ExportPolicy`, and `vault.v1.BundleSummary` sat beyond depth 2. In `routed_e2e`, the model read Vimanam's printed `--schema` hints, triggered `fetch_schemas` in **`3/3` trials on both tasks**, and reached **`6/6` (`3/3`)** and **`5/5` (`3/3`)** on Turn 3 (`mean_turns = 2.20`, overall `followup_rate = 0.20`).
3. **Small-spec vs. large-spec crossover (and latency trade-off)**:
   - **Small specs (`<15 KB` / `<10k` Claude tokens)**: passing raw `.proto` or SpaceX SDL in one turn uses fewer tokens and lower latency (`1.3–2.3 s` vs `4.0–6.7 s`) than 2–3 turn routing.
   - **Large specs (`>1 MB` / `>400k` Claude tokens)**: `routed_e2e` cuts Claude API input tokens by **47×–55×** (`8,641`, `8,504`, `7,381`, `9,616` vs `408k–479k`), cutting observed API cost across the 8 fitting tasks by **160.9×** (`$0.0106` vs `$1.7055`) at **2.84×** higher wall latency (`40.5 s` vs `14.2 s`) for 2–3 sequential turns.
4. **Product default hazard — unbounded `--schema` on cyclic OpenAPI specs ([#160](https://github.com/noemaforge/vimanam/issues/160))**: an earlier harness run invoked `vimanam spec3.json --schema customer --no-report` without `--schema-depth`, which expanded Stripe's transitive component graph into `1,427,889` chars (`559,554` Claude tokens, `$0.551` uncached). Passing `--schema-depth 2` on `--schema` calls reduced `--schema customer` by `102×` to `13,992` chars and brought `oa_stripe_customers` `routed_e2e` to **`24,940` Claude tokens (`$0.0037`, `3/3` pass)**. Because Vimanam's own depth-cutoff retrieval hints currently omit `--schema-depth`, bounding standalone `--schema` hints is tracked in [#160](https://github.com/noemaforge/vimanam/issues/160).
5. **Real product UX bug — synthetic `request.` prefix on inline OpenAPI request schemas ([#156](https://github.com/noemaforge/vimanam/issues/156))**: the only remaining failures across all 30 `routed_e2e` trials occurred on `required_fields` for `oa_batches` (`0/3`) and `oa_stripe_payment_intents` (`2/3` failed), both of which define inline (non-`$ref`) request bodies whose Markdown field rows carry a synthetic `request.` prefix.

## Tokenizer calibration: Claude API tokens vs `o200k_base` vs `chars / 4`

Vimanam's `--max-tokens`, `--stats`, and `--costs` use a fast `chars / 4` heuristic (`estimate_tokens` in `src/markdown/mod.rs`). Measuring net Claude API context tokens (`api_input_tokens_median - no_spec_baseline`) on `claude-haiku-5-5` alongside `tiktoken` (`o200k_base`) across payloads `>= 1,000` chars shows a consistent vendor gap (note: this calibration reflects one Claude model with `2–3` samples per raw format and `16` Markdown samples):

| Content format | Samples (`>=1 KB`) | Median chars / `o200k_base` | Median chars / Claude token | Median Claude / `o200k_base` ratio | Implication for `--max-tokens` (`chars / 4`) |
|---|---:|---:|---:|---:|---|
| **Vimanam Markdown** | `16` | `4.01` | `2.24` | **`1.65×`** | `chars / 4` tracks `o200k_base` closely, but **undercounts Claude tokens by ~1.65×–1.79×** (`--max-tokens 1600` ≈ `2,650–2,850` Claude tokens; tracked in [#165](https://github.com/noemaforge/vimanam/issues/165)) |
| **GraphQL SDL** | `2` | `3.83` | `2.38` | **`1.60×`** | Dense punctuation inflates Claude tokens ~1.68× above `chars / 4` |
| **Protobuf / gRPC** | `3` | `4.23` | `2.20` | **`1.90×`** | Compact synthetic `.proto` identifiers inflate Claude tokens relative to `o200k_base` |
| **OpenAPI YAML** | `3` | `4.89` | `3.38` | **`1.45×`** | Indentation compresses well in `o200k_base` (`4.89` chars/tok) and moderately in Claude (`3.38` chars/tok) |

|---|---:|---:|---:|---:|---:|---:|
| **Stripe OpenAPI 3.0** (`7.9 MB` JSON) | `1,418,244` | `2,079,211` (`5.86`) | `1,095,911` | `1,147,353` (`4.19`) | `3,825` (`POST /v1/customers`) | `99.7%` fewer |

## Trade-offs and tracked issues in v2.2.0

<Aside type="caution" title="Measured limits and open tracking issues">
  - **OpenAPI `diff` scaling & contract v2 JSON size ([#152](https://github.com/noemaforge/vimanam/issues/152), [#159](https://github.com/noemaforge/vimanam/issues/159))**: unmemoized recursive `$ref` expansion times out past `15 s` on Stripe's cyclic `7.9 MB` spec, and v2 JSON unconditionally embeds both full `old`/`new` surfaces (`37.1 MB` on OpenAI `4.9 MB`; `17.1 MB` for a 1-change GitHub GraphQL diff).
  - **OpenAPI 3.1 gaps ([#166](https://github.com/noemaforge/vimanam/issues/166), [#167](https://github.com/noemaforge/vimanam/issues/167))**: `type: ["T", "null"]` drops `"null"` during deserialization (missing `| null` and nullability diffs), and single-value `enum: ["x"]` ↔ `const: "x"` refactors emit false breaking findings.
  - **OpenAPI `diff` media-type scope ([#154](https://github.com/noemaforge/vimanam/issues/154))**: `vimanam diff` currently compares only the first media type in each request body or response `content` map.
  - **Inline OpenAPI `request.` prefix ([#156](https://github.com/noemaforge/vimanam/issues/156))**, **unbounded `--schema` hints ([#160](https://github.com/noemaforge/vimanam/issues/160))**, and **per-field stderr truncation spam ([#161](https://github.com/noemaforge/vimanam/issues/161))**.
  - **Protobuf gaps**: streaming changes omitted from `--breaking wire` ([#153](https://github.com/noemaforge/vimanam/issues/153)), mixed `.pb` vs `.proto` `descriptor.proto` drift ([#155](https://github.com/noemaforge/vimanam/issues/155)), Protobuf Editions tracking ([#157](https://github.com/noemaforge/vimanam/issues/157)), per-side `-I` roots for file-to-file diff ([#162](https://github.com/noemaforge/vimanam/issues/162)), and Git blob batching ([#164](https://github.com/noemaforge/vimanam/issues/164)).
  - **GraphQL SDL duplicate field validation ([#163](https://github.com/noemaforge/vimanam/issues/163))**: duplicates are rejected in `extend type` but silently accepted inside a single `type` block.
  - **Token estimator offset for Claude ([#165](https://github.com/noemaforge/vimanam/issues/165))**: `chars / 4` undercounts Claude tokens by ~`1.65×` on Vimanam Markdown.
</Aside>
