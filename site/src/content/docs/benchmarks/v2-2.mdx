## Task-accuracy evaluation

<Aside type="tip" title="Summary">
  - **Large specs (over 1 MB) are where Vimanam pays off.** Routed slices used **`46×`–`60×` fewer** Claude input tokens than the raw spec on the four large tasks that fit in context. They matched raw accuracy (`19 / 19` prefix-tolerant, `18 / 19` strict) and cost **`208×` less** when both sides were uncached.
  - **Caching the raw spec does not close the gap.** A fully cached raw spec still cost **`33×`** more than a cached routed run, and **`10.8×`** more than an *uncached* routed run.
  - **On small specs, pass the raw spec.** Below about `30 KB`, the raw spec used `2.1×` fewer tokens, cost `2.2×` less, answered `2×`–`5×` faster, and scored the same `28 / 28`.
  - **Past the context limit, routing is the only option that works.** Both Stripe `7.9 MB` tasks failed raw with `Prompt is too long`. Routed scored `8 / 8`.
</Aside>

Eleven contract tasks ran serially (`--workers 1`) on `claude-haiku-5-5` through `claude -p`, with zero tools and an isolated system prompt. Each cell got `3` graded trials, and the large raw specs got `1`. Each trial was graded on deterministic JSON assertions (`55` in total), with no LLM judge. The six conditions were:

1. **`no_spec`** *(memorization control)*: the question alone, with no contract context.
2. **`summary`**: `vimanam --detail summary --no-report`.
3. **`routed_e2e`** *(the real workflow)*:
   - Turn 1 reads the summary and picks `--operation-id` / `--operation` plus up to `3` `--schema` names.
   - The harness runs `vimanam` with `--schema-depth 2` on every call.
   - Turn 2 either answers or returns `{"fetch_schemas": [...]}` (up to `3` names) for one follow-up call, and Turn 3 answers.
   - Totals sum every turn's tokens, cost, and latency.
4. **`fixed_slice`**: one `--operation … --detail full --include-schemas --schema-depth 2` call with no extra `--schema`. This is a deliberately naive single-turn baseline.
5. **`oracle_slice`**: the same operation slice plus `--schema` (depth 2) for exactly the named types that hold the answers. The harness refuses to run unless every answer marker is present in this slice.
   - Comparing **routed against oracle** isolates routing quality.
   - Comparing **oracle against raw** isolates how readable the slice is.
6. **`raw_spec`**: raw YAML, JSON, concatenated `.proto` files, or `.graphql` SDL.

**Cache protocol.** Every graded trial prepends a fresh nonce to each prompt, so every graded call is a cold-cache call. Right after trial 1, its exact prompts are replayed with the same nonce to measure the warm-cache cost, and that replay is not graded. The earlier `161×` cost figure mixed cold raw calls with warm routed repeats. Cold against cold, that same data gave about `102×`.

**Tasks.**
- `pb_ledger_stream`, `pb_fleet_dispatch`, and `pb_vault_audit` are synthetic multi-file `.proto` services, so memorization cannot help.
- `pb_otel_trace_export` is the real OpenTelemetry `TraceService.Export`. Its answers sit beyond depth 2 (`Span`, `ScopeSpans`, `Status`).
- The other tasks are public OpenAPI and GraphQL specs pinned to fixed commits.

**Size classes** use the raw spec size:
- *large*: over `1 MB`, fits in context (OpenAI ×3, GitHub `createIssue`)
- *small*: under `30 KB` (the four protos and SpaceX)
- *too large*: the two Stripe `7.9 MB` tasks

1. Some answers named fields with the synthetic `request.` prefix Vimanam renders on inline request bodies, for example `request.input_file_id` ([#156](https://github.com/noemaforge/vimanam/issues/156)). The grader accepts the prefix because the field is unambiguous. Strict scoring fails `required_fields` in `5` routed trials: `oa_batches` `3/3` and `oa_stripe_payment_intents` `2/3`. The raw spec never produced the prefix, so the gap is a real cost of #156.
2. The oracle's misses are all `response_schema`: the model described the schema ("response: Batch object …") instead of naming it, even though the name was in its context.
3. GraphQL `--include-schemas` never shows argument input types such as `CreateIssueInput` or `LaunchFind`, even at depth `24` ([#170](https://github.com/noemaforge/vimanam/issues/170)). The routed and oracle conditions recover by naming them with `--schema`.
4. `no_spec` scored `0/6` on all three trials here, but `6/6` on `2` of `7` trials across every run of this task. Haiku sometimes knows the OpenTelemetry protos from training data.

### Findings

1. **Routing picked the right target every time.** Turn 1 chose the expected operation and `vimanam` exited `0` in all `33 / 33` routed trials. The routed condition scored `55 / 55`, at or above the oracle's `53 / 55`. On this suite, routing lost no information compared with the hand-picked slice.
2. **The follow-up path fires when it is needed and not otherwise.**
   - On the three tasks whose answers sit beyond depth 2 (`pb_fleet_dispatch`, `pb_vault_audit`, and the real-spec `pb_otel_trace_export`), the model called `fetch_schemas` in `9 / 9` trials and answered fully on Turn 3.
   - It requested no follow-up in any of the other `24` trials.
   - Because `no_spec` sometimes answers OTel from memory, that task proves the follow-up path runs on a real spec, not that the context was needed.
   - The synthetic `fleet/v2` and `vault/v1` tasks remain the memorization-free evidence.
3. **`fixed_slice` measures depth-2 truncation, not routing.**
   - It scored `56.4%` because a bare operation slice at depth 2 omits answer-holding types. Its coverage was only `62.1%`.
   - Both GraphQL tasks score `2/5` because of [#170](https://github.com/noemaforge/vimanam/issues/170).
   - Use `oracle_slice` to judge slice readability. It scored `96.4%` against raw's `100%` on tasks that fit, and its only misses are answer format.
4. **The crossover is around tens of kilobytes.**
   - Below about `30 KB`, raw beats routing on tokens, cost, and latency: routing takes 2–3 sequential turns at `3.6`–`9.7 s` against `1.4`–`2.3 s` for raw.
   - Above `1 MB`, routing is decisively cheaper at the same accuracy, but `1.5×` slower in API latency (`20.1 s` against `13.8 s` across the four large tasks).
5. **Unbounded slices are a default hazard ([#160](https://github.com/noemaforge/vimanam/issues/160)).** Without `--schema-depth`, the full transitive expansion of an operation slice runs to:
   - Stripe `POST /v1/customers`: `1,277,808` characters
   - GitHub `createIssue`: `1,200,523` characters

   This harness passes `--schema-depth 2` on every call.

## Tokenizer calibration: Claude API tokens vs `o200k_base` vs `chars / 4`

Vimanam's `--max-tokens`, `--stats`, and `--costs` use a fast `chars / 4` heuristic (`estimate_tokens` in `src/markdown/mod.rs`). Measuring net Claude API context tokens (`api_input_tokens_median - no_spec_baseline`) on `claude-haiku-5-5` alongside `tiktoken` (`o200k_base`) across payloads `>= 1,000` chars shows a consistent vendor gap. This calibration covers one Claude model, with `2`–`4` samples per raw format and `28` Markdown samples:

| Content format | Samples (`>=1 KB`) | Median chars / `o200k_base` | Median chars / Claude token | Median Claude / `o200k_base` ratio | Implication for `--max-tokens` (`chars / 4`) |
|---|---:|---:|---:|---:|---|
| **Vimanam Markdown** | `28` | `3.87` | `2.34` | **`1.62×`** | `chars / 4` tracks `o200k_base` closely, but **undercounts Claude tokens by ~1.7×** (`--max-tokens 1600` ≈ `2,700` Claude tokens; tracked in [#165](https://github.com/noemaforge/vimanam/issues/165)) |
| **GraphQL SDL** | `2` | `3.83` | `2.38` | **`1.60×`** | Dense punctuation inflates Claude tokens ~1.68× above `chars / 4` |
| **Protobuf / gRPC** | `4` | `4.22` | `2.27` | **`1.85×`** | Compact synthetic `.proto` identifiers inflate Claude tokens relative to `o200k_base` |
| **OpenAPI YAML** | `3` | `4.89` | `3.38` | **`1.45×`** | Indentation compresses well in `o200k_base` (`4.89` chars/tok) and moderately in Claude (`3.38` chars/tok) |

## Trade-offs and tracked issues in v2.2.0

<Aside type="caution" title="Measured limits and open tracking issues">
  - **OpenAPI `diff` scaling & contract v2 JSON size ([#152](https://github.com/noemaforge/vimanam/issues/152), [#159](https://github.com/noemaforge/vimanam/issues/159))**: unmemoized recursive `$ref` expansion times out past `15 s` on Stripe's cyclic `7.9 MB` spec, and v2 JSON unconditionally embeds both full `old`/`new` surfaces (`37.1 MB` on OpenAI `4.9 MB`; `17.1 MB` for a 1-change GitHub GraphQL diff).
  - **Breaking-change precision ([#169](https://github.com/noemaforge/vimanam/issues/169), [#171](https://github.com/noemaforge/vimanam/issues/171))**: on the one real OpenAI diff reconciled so far, about `6%` of breaking findings were real (`4` of `62`, covering `2` actual changes). Removing a response enum member is wrongly marked breaking, which accounts for `49` of the `58` false positives. Precision across many real version pairs is not yet measured. Until it is, treat `--fail-on-breaking` on OpenAPI 3.1 as high-recall and low-precision.
  - **GraphQL argument input types ([#170](https://github.com/noemaforge/vimanam/issues/170))**: `--include-schemas` does not link or expand argument input objects, so operation slices omit them.
  - **OpenAPI 3.1 gaps ([#166](https://github.com/noemaforge/vimanam/issues/166), [#167](https://github.com/noemaforge/vimanam/issues/167))**: `type: ["T", "null"]` drops `"null"` during deserialization (missing `| null` and nullability diffs), and single-value `enum: ["x"]` ↔ `const: "x"` refactors emit false breaking findings.
  - **OpenAPI `diff` media-type scope ([#154](https://github.com/noemaforge/vimanam/issues/154))**: `vimanam diff` currently compares only the first media type in each request body or response `content` map.
  - **Inline OpenAPI `request.` prefix ([#156](https://github.com/noemaforge/vimanam/issues/156))**, **unbounded `--schema` hints ([#160](https://github.com/noemaforge/vimanam/issues/160))**, and **per-field stderr truncation spam ([#161](https://github.com/noemaforge/vimanam/issues/161))**.
  - **Protobuf gaps**: streaming changes omitted from `--breaking wire` ([#153](https://github.com/noemaforge/vimanam/issues/153)), mixed `.pb` vs `.proto` `descriptor.proto` drift ([#155](https://github.com/noemaforge/vimanam/issues/155)), Protobuf Editions tracking ([#157](https://github.com/noemaforge/vimanam/issues/157)), per-side `-I` roots for file-to-file diff ([#162](https://github.com/noemaforge/vimanam/issues/162)), and Git blob batching ([#164](https://github.com/noemaforge/vimanam/issues/164)).
  - **GraphQL SDL duplicate field validation ([#163](https://github.com/noemaforge/vimanam/issues/163))**: duplicates are rejected in `extend type` but silently accepted inside a single `type` block.
  - **Token estimator offset for Claude ([#165](https://github.com/noemaforge/vimanam/issues/165))**: `chars / 4` undercounts Claude tokens by ~`1.7×` on Vimanam Markdown.
</Aside>
