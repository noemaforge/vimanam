Production OpenAPI and GraphQL specs often exceed an LLM's context window by an order of magnitude. Vimanam gives you deterministic sizing, surgical selection, and depth bounds so coding agents load only what a task requires.

## Size a spec before rendering

Run `--stats` to measure each service's endpoint count and approximate token size (`chars / 4`) without writing Markdown:

```bash
vimanam openapi.yaml --stats --detail standard
```

```text
SERVICE       ENDPOINTS   ~TOKENS
Chat                 12      1840
Embeddings            2       310
Fine-tuning          14      2190
TOTAL                28      4120
```

Each service row measures a standalone render of that service, while `TOTAL` measures one whole-document render. Multi-tag endpoints count in each tagged service row and once in `TOTAL`.

## Find token hotspots with `--costs`

Use `--costs` to identify which endpoints and shared `$ref` schemas drive token volume:

```bash
vimanam openapi.yaml --costs --detail full --include-schemas
```

`--costs` reports three sections:

- **Per-endpoint slice costs**: estimated tokens to render each operation with its reachable schemas.
- **Per-schema definition and amplification**: compares reading a schema once versus expanding it inline across every reference site.
- **Hotspots**: ranks the largest endpoint slices and highest-amplification schemas so you know where `--schema-depth` or `--schema-field` pays off most.

<Aside type="note" title="Dry-run flag conflicts">
  `--stats` and `--costs` are dry runs that print tables to stdout. Both conflict with `-o`, `--max-tokens`, `--split`, `--output-mode skill`, and `--schema` / `--schema-field`.
</Aside>

## Select exact operations

Use `--operation` or `--operation-id` when a task touches specific endpoints:

```bash
# OpenAPI exact METHOD + path template (repeatable)
vimanam openapi.yaml \
  --operation "POST /chat/completions" \
  --operation "GET /models/{model}" \
  --detail full --include-schemas --flat --no-report

# Match by case-sensitive operationId
vimanam openapi.yaml --operation-id createChatCompletion --detail full --include-schemas

# Protobuf RPC or GraphQL root field
vimanam trace_service.proto -I . --operation "RPC opentelemetry.proto.collector.trace.v1.TraceService.Export" --detail full --include-schemas
vimanam schema.graphql --operation "QUERY Query.repository" --detail full --include-schemas
```

Behavior rules for exact selectors:

- `--operation` matches `METHOD` case-insensitively and the path template byte for byte (Swagger 2 `basePath` excluded).
- Both flags repeat and combine as a union, then intersect with `--service-filter`, `--path-filter`, `--method-filter`, and `--exclude-deprecated`.
- Any selector that matches nothing in the spec exits with status `1` and suggests the closest valid operation name.
- Use `--flat` to render multi-tag operations once instead of repeating them under each service heading.

## Read named schemas and subtrees directly

When one schema is huge, query the type or a single JSON Pointer subtree directly:

```bash
# Read one named schema (complete metadata, even if unreferenced by an endpoint)
vimanam openapi.yaml --schema CreateChatCompletionRequest --no-report

# Prune unrelated siblings while keeping ancestor metadata
vimanam openapi.yaml \
  --schema-field 'CreateChatCompletionRequest#/properties/response_format' \
  --schema-field 'CreateChatCompletionRequest#/properties/tools' \
  --no-report
```

Pointers follow RFC 6901 escaping (`~1` for `/`, `~0` for `~`) and cross `$ref` boundaries safely, including recursive schemas. Standalone schema reads always include full metadata and suppress the endpoint hygiene report.

## Bound schema traversal with `--schema-depth`

Add `--schema-depth <0..=24>` to stop expanding deeply nested objects, arrays, compositions, or `$ref` links after `N` edges from each root:

```bash
vimanam openapi.yaml \
  --operation "POST /v1/customers" \
  --detail full --include-schemas --schema-depth 2 --no-report
```

Every truncated branch preserves its field type and requiredness and prints the exact `--schema`, `--schema-field`, or operation command needed to inspect deeper fields. Those commands carry a bounded `--schema-depth` too: a linked schema is re-rooted at the same depth, and a re-render of the same root goes that many levels past the cutoff, so following a hint never triggers an unbounded expansion. On stderr, truncated fields that share a retrieval command are summarized on one line (`... at depth 2 for 89 fields (amount_details.discount_amount, ...); retrieve full detail: ...`). Without `--schema` or `--schema-field`, `--schema-depth` requires `--detail full --include-schemas`.

### Default bound for large component graphs

When `--schema-depth` is omitted, a selected slice (standalone `--schema` / `--schema-field`, or `--operation` / `--operation-id` with `--detail full --include-schemas`) whose roots transitively reach more than 200 component schemas is bounded at `--schema-depth 2`. A notice on stderr (also under `--stats` and `--costs`) and a blockquote under the Markdown title say so, and `--costs` adds a `Schema depth: automatic` line and measures every row at that depth. Highly connected specs hit this: Stripe's `customer` schema and GitHub's GraphQL `createIssue` reach 830–920 components and rendered 1.2–1.4 MB unbounded, against roughly 4–18 KB at depth 2. Smaller graphs, whole-document renders, and any explicit `--schema-depth` are unchanged; pass `--schema-depth N` (up to 24) to choose a different bound.

`--inline-schemas` has a second, separate bound. Inline expansion re-expands every acyclic path through the component graph at each use site, so a densely cross-linked spec grows exponentially even with cycle detection (on 2.2.0, a whole-document Stripe render never finished). Without `--schema-depth`, vimanam first counts, without rendering, how many schema rows the inline tables would hold; past 2,000,000 rows (a few hundred MB of Markdown) the render is bounded at `--schema-depth 2`. The count follows the view: the default service grouping renders an operation under each of its tags, so a multi-tag operation counts once per tag. This applies to whole documents as well as selected slices, and to `--max-tokens`, `--stats` and `--costs`. The stderr notice reads:

```text
vimanam: --inline-schemas would expand more than 2000000 schema rows and --schema-depth is not set; bounding schema expansion at --schema-depth 2 (pass --schema-depth 0..=24 to choose, or drop --inline-schemas to render each component schema once)
```

and the blockquote under the Markdown title:

```text
> Schema expansion is bounded at --schema-depth 2: --inline-schemas would expand more than 2000000 schema rows. Follow the per-row retrieval commands, pass --schema-depth N (0..=24) to choose another bound, or drop --inline-schemas to render each component schema once.
```

Every cut row keeps its type and requiredness and carries a `--schema NAME --schema-depth 2` retrieval command, as with any `--schema-depth`. Renders at or under the budget are byte-identical to earlier releases; real specs stay far below it (a 10 MB GitHub REST spec renders about 63,000 rows inline). An inline render above the budget that used to finish, slowly, is now bounded too: for example, a synthetic 26-component graph that wrote 193 MB (2,022,256 rows) in 3.7 s now renders at depth 2 with the notice. Pass an explicit `--schema-depth N` to choose a deeper bound. Linked mode, the default, is never affected.

The `--costs` amplification model measures one inline expansion of every used schema separately, so it uses a smaller per-schema budget of 25,000 rows (the largest single expansion in the real specs measured so far is under 3,000). A schema past it is measured by the first 2,000 rows of its expansion only and marked `inline-bounded` in the NOTES column and the hotspot list (`at least ~N tokens inline`). Its INLINE/USE figure is then a lower bound, but still large enough to rank the schema as a hotspot.

Inline request and response tables label their root row `(request body)` / `(response body)` and list body fields by their real JSON paths (`input_file_id`, `metadata.key`, `tags[]`), so the names can be copied straight into a request.

## Step detail down with `--max-tokens`

For single-file overviews, `--max-tokens <N>` starts at your requested `--detail` level and steps down (`full` → `standard` → `basic` → `summary`) until the body fits:

```bash
vimanam openapi.yaml --service-filter Payments --detail full --max-tokens 6000 --no-report
```

- Pass `--no-report` when feeding output to a model so the Spec Hygiene Report is omitted.
- Explicit `--schema` and `--schema-field` selections stay intact even when over budget and emit an overage notice on stderr and in Markdown.
- Use `--output-mode skill` instead of `--max-tokens` when an agent should load full schemas selectively across files.
