`vimanam diff` compares two contract versions and classifies every change as breaking, non-breaking, or needing review. You can compare local files directly or read committed blobs straight from Git refs without modifying your worktree.

## Compare two local files

```bash
# Markdown report with hygiene and token deltas, failing CI on breaking changes
vimanam diff old.yaml new.yaml --report --fail-on-breaking

# Machine-readable neutral contract v2 JSON
vimanam diff old.yaml new.yaml --format json -o diff.json

# Protobuf wire-only breaking gate (no protoc required)
vimanam diff old.proto new.proto -I proto --breaking wire --fail-on-breaking

# GraphQL schema diff with token-budgeted affected-operation context
vimanam diff old.graphql new.graphql --context --max-tokens 2000
```

Vimanam validates both inputs before creating or truncating any `-o` output file.

## Compare committed specs across Git refs

Run `vimanam diff` inside a Git worktree to compare tags, branches, or commit expressions directly from committed blobs:

```bash
# Auto-discover when --to-ref has one tracked OpenAPI spec
vimanam diff --from-ref v1.0.0 --to-ref HEAD --report --fail-on-breaking

# Anchor a specific path at --to-ref and follow Git renames back to --from-ref
vimanam diff --from-ref main --to-ref feature \
  --spec api/openapi.yaml --format json -o diff.json

# Protobuf Git-ref diff (resolved directly from Git blobs in memory)
vimanam diff --from-ref v1.0.0 --to-ref v2.0.0 \
  --spec proto/api.proto -I proto --breaking wire --fail-on-breaking

# GraphQL Git-ref diff on a single committed SDL or introspection file
vimanam diff --from-ref v1.0.0 --to-ref HEAD --spec schema.graphql --context
```

### Bypass rename discovery with `--from-spec` and `--to-spec`

When a spec was both moved and heavily rewritten past Git's 50% rename threshold, supply both paths explicitly:

```bash
vimanam diff --from-ref v1.0.0 --to-ref HEAD \
  --from-spec legacy/swagger.json \
  --to-spec api/openapi.yaml \
  --report
```

Key Git-ref guarantees:

- Reads committed blobs only; uncommitted edits and untracked worktree files never affect the diff.
- Automatic candidate discovery applies only to OpenAPI specs; Protobuf and GraphQL require `--spec` or paired `--from-spec`/`--to-spec`.
- Historical `.proto` imports stay confined to repository-relative `-I` roots and reject symlinked `.proto` files.

## OpenAPI moved-operation pairing

In OpenAPI Markdown and contract v2 JSON output, Vimanam pairs removed and added operations of the same HTTP method that moved to a new path:

1. Matches exact `(METHOD, path)` pairs first.
2. Pairs remaining removed and added operations of the same method by unique `operationId` across the full old and new specs.
3. Pairs remaining leftovers by path equality after normalizing whole `v<digits>` version segments (`/api/v1/items` ↔ `/api/v2/items`).

A paired move emits one breaking `operation_moved` change (`Endpoint moved` in Markdown) followed by the operation's inner parameter, schema, and pagination changes. Ambiguous keys stay separate removals and additions. Pass `--exact-paths` to disable move pairing and restore exact matching.

## Shared components are reported once

OpenAPI `$ref` targets are compared as edges, the way `oasdiff` does: each pair of referenced components is compared once, and a change inside a shared component is reported once per usage direction, with every operation that reaches it listed under the tables:

```markdown
| Component schema changed | component `Widget` | response `/properties/pricing` added (3 operations) |

## Affected operations

### `Widget`

- `GET /widgets` response 200
- `POST /widgets` response 201
- `GET /widgets/{id}` response 200
```

A component sent in requests and returned in responses gets one row per direction, each classified by its own rule table, so `--fail-on-breaking` fails when either direction breaks. Changes inside an operation's own inline schemas stay on that operation. This keeps densely cross-linked specs fast: a change under Stripe's 97-node reference cycle is one row, not one per reference path (millions).

Only schema positions the rule tables understand (the schema itself, `properties`, `items`, `additionalProperties`, `allOf`/`oneOf`/`anyOf` and `not`) count as uses of a component. A `$ref` under `default`, `const`, an `enum` member, `if`/`then`/`else`, `prefixItems` or `$defs` is expanded in place instead, so a change reached that way appears at its full pointer (for example `/default/type`, or `/enum/<member>/type` for an `enum` member that is a reference) and is classified `review`. Rewriting an `enum` member without changing what it resolves to (pointing it at an identical component, or inlining it) is one `review` change, not a removed and an added member.

A schema that moves between a `$ref` and an inline copy is compared field by field, also for a recursive component: writing `$ref: Node` as an inline copy of `Node` unrolled a level or two is no change, and a change inside the unrolled copy is reported where it is, with its own verdict. The expansion is bounded (64 levels on one path, 4,096 expansions per schema): past that the reference is compared as written and fails closed: the `$ref` row there is breaking, so a change hidden behind the limit still trips `--fail-on-breaking`.

A `definitions` entry that is not a valid schema (for example `"required": "id"` instead of `["id"]`) is still compared, as written, so a change inside it is reported. It fails closed: a change there that the rule tables would leave to review is breaking (also where the entry is expanded against an inline schema), so `--fail-on-breaking` trips on any change inside an invalid entry. The report starts with a `> **Warning:**` line naming the entry, the same warning goes to stderr, and `--format json` lists it under `warnings`. Markdown rendering leaves such an entry out, as before.

## Every media type is compared

A request body or response with several media types (`content` keys) is compared media type by media type. Media types match the way RFC 9110 compares them: the type, the subtype and parameter names case-insensitively, and ignoring whitespace around `;`. So `Application/JSON` is the same media type as `application/json`, a respelling reports nothing, and rows name a matched media type as the old spec writes it. A media type one side lacks is its own row:

```markdown
| Request media type removed | `POST /widgets` | `application/xml` |
| Response schema changed | `GET /widgets` | 200 `application/xml` `/properties/id/type` changed `string` → `integer` |
```

| Change | Severity |
|---|---|
| Request media type removed (clients that send it fail) | `breaking` |
| Request media type added | `non-breaking` |
| Response media type removed (clients that ask for it with `Accept` fail) | `breaking` |
| Response media type added | `non-breaking` |

A shared component reached through two media types of one response is still one row, with both media types listed under `## Affected operations`. When each side has exactly one media type and it is the same one, or a response gains or loses its whole body, the body or response is compared as before, so specs whose bodies and responses keep a single media type report exactly what they did. Swagger 2 bodies and responses name no media type (`consumes` and `produces` are not compared), so a Swagger 2 → OpenAPI 3 migration compares the first schemas.

Some matching is deliberately conservative, so it can over-report but never hides a change:

- **Parameter values are compared as written.** `application/json` → `application/json; charset=utf-8`, or `charset=utf-8` → `charset=UTF-8`, is a removed media type (`breaking`) plus an added one.
- **Wildcards match only themselves.** `*/*` or `application/*` is not matched against the concrete types it covers, so `*/*` → `application/json` is a removal plus an addition.
- **Two spellings of one media type in one `content` map** are one media type: the first is compared, the rest are ignored.
- **Adding a response media type is `non-breaking`** on the assumption that a server keeps answering an `Accept` header it answered before with the same type. A client that sends `Accept: */*` (or no `Accept`) to a server that then prefers the new type may receive it; Vimanam does not model the server's content negotiation.

## Include hygiene and token deltas with `--report`

Pass `--report` to append a `Deltas` section comparing both versions:

- Spec hygiene check counts for old versus new specs (OpenAPI) or entity/type/operation counts (Protobuf and GraphQL)
- Estimated full-documentation token sizes (`chars / 4`) and net token delta

## Exit codes for CI gates

| Exit code | Meaning |
|---:|---|
| `0` | Diff completed cleanly, or `--fail-on-breaking` was not set, or only non-breaking/review changes exist |
| `1` | Input, parse, Git-ref, or flag validation error (no output file created) |
| `3` | Breaking changes found when `--fail-on-breaking` is enabled (complete report is written before exiting) |

<Aside type="note" title="Review changes never fail CI">
  Changes classified as `review` — such as OpenAPI pagination changes, default-value changes, or GraphQL output enum additions — appear in the report and JSON output but never trigger exit code `3`.
</Aside>
