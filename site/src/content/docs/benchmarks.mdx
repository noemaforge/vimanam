## Task-accuracy evaluation: end-to-end routed workflow vs oracle slice vs raw spec

Extracting one operation out of 612 is selection, not compression. To measure whether Vimanam actually helps a coding agent answer exact contract questions without human oracle hints, ten contract tasks across OpenAI OpenAPI 3.0 (`1.3 MB` YAML), Stripe OpenAPI 3.0 (`7.9 MB` JSON), gRPC Health (`health-v1.20.0.proto`), OpenTelemetry Collector (`trace_service.proto` and `metrics_service.proto` with transitive imports), SpaceX Land GraphQL (`12 KB` SDL), and GitHub GraphQL (`1.2 MB` SDL) ran under five conditions on the same model (`claude-haiku-5-5`, zero tools, isolated system prompt):

1. **`no_spec`** *(memorization control, 3 trials/task)*: question only, no contract context.
2. **`summary`** *(3 trials/task)*: `vimanam --detail summary --no-report`.
3. **`routed_e2e`** *(real workflow, 3 trials/task)*: Turn 1 reads `vimanam --detail summary` and selects `--operation-id` / `--operation` and optional `--schema` names. The harness runs `vimanam` with a uniform `--schema-depth 2` across all tasks. Turn 2 answers from the retrieved slice or requests follow-up schemas via `{"fetch_schemas": [...]}`. Totals sum **all turns' Claude API input tokens, wall latency, and USD cost**.
4. **`oracle_slice`** *(3 trials/task)*: single-turn harness-selected `vimanam --operation ... --detail full --include-schemas --schema-depth 2` (depth `3` on OTel; plus `--schema` for GraphQL input types), separating routing from slice readability.
5. **`raw_spec`** *(3 trials on small specs; 1 trial on >100k-token specs)*: raw YAML, raw JSON, concatenated `.proto` + transitive imports, or raw `.graphql` SDL — executed on all 10 tasks, including both Stripe `7.9 MB` JSON tasks (`1,418,244` `o200k_base` tokens), which returned `exit 1`, `"terminal_reason": "blocking_limit"`, and `"Prompt is too long"` (`0` output tokens, `$0.00` billed).

Every trial was graded deterministically on strict JSON assertions (`50` assertions across `10` tasks; `138` total executed LLM trials; no LLM judge).

### Key findings and product issues surfaced by the evaluation

1. **Routing reliability (`30 / 30` trials) and where routing beats raw specs**: in `routed_e2e`, Claude Haiku selected a valid `vimanam` operation selector on Turn 1 in **100% of trials (`30 / 30`)**. However, the payoff depends strongly on spec size:
   - **Small specs (`<50 KB` / `<20k` Claude tokens)**: passing raw `.proto` or SpaceX SDL in one turn uses **fewer tokens, lower cost, and lower latency** than 2-turn routing (`pb_health_watch`: `2,167` raw vs `5,881` routed; `pb_otel_trace`: `11,844` vs `21,153`; `pb_otel_metrics`: `17,230` vs `33,959`).
   - **Large specs (`>1 MB` / `>400k` Claude tokens)**: `routed_e2e` cuts Claude API input tokens by **47×–66×** (`8,729`, `6,906`, `6,178`, `9,586` vs `408k–479k`).
2. **Real product UX bug — synthetic `request.` prefix on inline OpenAPI request schemas ([#156](https://github.com/noemaforge/vimanam/issues/156))**: both `POST /batches` and `POST /v1/payment_intents` define inline (non-`$ref`) request bodies. Vimanam renders their fields as `request.input_file_id`, `request.amount`, etc., causing `routed_e2e` to fail the `required_fields` assertion `0/3` on both tasks when the model echoes the synthetic prefix verbatim.
3. **Why `routed_e2e` outperformed `oracle_slice` on OpenTelemetry (`96.0%` vs `76.2%`)**: single-turn `oracle_slice` at `--schema-depth 3` stopped before `ExportTracePartialSuccess` and `ExportMetricsPartialSuccess`, so the model declined to guess omitted fields (`3/7` and `2.33/5`). In `routed_e2e`, the router requested those nested message names via `--schema` directly and scored **`6.33/7`** (`2/3` exact) on trace and **`5/5`** (`3/3` exact) on metrics.
4. **Operational pitfall — always pair `--schema` with `--schema-depth` on cyclic specs**: in `oa_stripe_customers`, two of three `routed_e2e` trials added `--schema customer` without a `--schema-depth` cap, pulling `559,554` Claude tokens of Stripe's transitively connected schema graph (`$0.551` uncached). Trial 2 skipped `--schema customer`, relied solely on `--operation-id PostCustomers --schema-depth 2`, and still passed **`4/4`** in **`19,712` Claude tokens (`$0.0045`)**.

## Tokenizer calibration: Claude API tokens vs `o200k_base` vs `chars / 4`

Vimanam's `--max-tokens`, `--stats`, and `--costs` use a fast `chars / 4` heuristic (`estimate_tokens` in `src/markdown/mod.rs`). Because tokenizers diverge sharply across formats and vendors, we measured **actual Claude API context tokens** (`api_input_tokens_median - no_spec_baseline_tokens`) alongside `tiktoken` (`o200k_base`) and `chars / 4` across all eval payloads `>= 1,000` chars:

| Content format | Samples (`>=1 KB`) | Median chars / `o200k_base` | Median chars / Claude token | Median Claude / `o200k_base` ratio | Implication for `--max-tokens` (`chars / 4`) |
|---|---:|---:|---:|---:|---|
| **Vimanam Markdown** | `16` | `4.11` | `2.40` | **`1.65×`** | `chars / 4` tracks `o200k_base` within ~3%, but **undercounts Claude tokens by ~1.67×** (`--max-tokens 1600` ≈ `2,650` Claude tokens) |
| **GraphQL SDL** | `2` | `3.83` | `2.38` | **`1.60×`** | Dense punctuation inflates Claude tokens ~1.68× above `chars / 4` |
| **Protobuf / gRPC** | `3` | `4.26` | `2.72` | **`1.57×`** | Claude tokens run ~1.47× above `chars / 4` |
| **OpenAPI YAML** | `3` | `4.89` | `3.38` | **`1.45×`** | Repeated indentation compresses well in `o200k_base` (`4.89` chars/tok) and moderately in Claude (`3.38` chars/tok) |

Full-spec `o200k_base` BPE sizes versus full Markdown and focused single-operation slices:

| Public specification | Raw `o200k_base` BPE | Raw `chars / 4` (chars/BPE) | Full Markdown `o200k_base` BPE | Full MD `chars / 4` (chars/BPE) | Focused slice `o200k_base` BPE | Selection ratio (BPE) |
|---|---:|---:|---:|---:|---:|---:|
| **Stripe OpenAPI 3.0** (`7.9 MB` JSON) | `1,418,244` | `2,079,211` (`5.86`) | `1,095,911` | `1,147,353` (`4.19`) | `3,825` (`POST /v1/customers`) | `99.7%` fewer |
| **OpenAI OpenAPI 3.0** (`1.3 MB` YAML) | `281,146` | `343,997` (`4.89`) | `151,987` | `154,266` (`4.06`) | `1,286` (`POST /chat/completions`) | `99.5%` fewer |
| **GitHub GraphQL API** (`1.2 MB` SDL) | `286,673` | `305,959` (`4.27`) | `414,860` | `427,790` (`4.12`) | `9,902` (`Query.repository`) | `96.5%` fewer |

## External baseline comparisons

All four format-specific external tools (`oasdiff 1.39.0`, `buf 1.75.0`, `graphql-inspector 7.0.8`, and `protoc-gen-doc 1.5.1`) ran on the same machine against real multi-MB open-source revisions plus targeted compatibility smoke tests.

### 1. OpenAPI: `vimanam diff` vs `oasdiff 1.39.0`

#### Large-spec revision diff speed (OpenAI `4.9 MB` `openapi.json`, `a01e367 -> 373f26a`, 5 runs)

| OpenAPI mutation case | `vimanam diff` (v2.2.0) | `oasdiff breaking` (1.39.0) | Notes |

| Optional response property added | Non-breaking (`field_added`) | Non-breaking | Exact agreement |
| Versioned path moved (`/v1/items -> /v2/items`) | Breaking (`operation_moved`) | Breaking (`api-path-removed-without-deprecation`) | Vimanam pairs the move and attributes inner changes; `oasdiff` reports separate path removal |

## Upgrade analysis: v2.2.0 vs v2.1.0

## Trade-offs and known limits

<Aside type="caution" title="Measured trade-offs and tracked issues in v2.2.0">
  - **OpenAPI `diff` media-type scope ([#154](https://github.com/noemaforge/vimanam/issues/154))**: `vimanam diff` currently compares only the first media type in each request body or response `content` map, whereas `oasdiff` compares every media type.
  - **OpenAPI `diff` scaling on cyclic multi-MB specs and v2 JSON size ([#152](https://github.com/noemaforge/vimanam/issues/152))**: on OpenAI's `4.9 MB` spec, contract v2 JSON emits `37.1 MB` (`1,617 ms` vs `272 ms` for Markdown). On Stripe's `7.9 MB` spec, unmemoized cyclic `$ref` expansion causes `vimanam diff` to exceed `15 s` while `oasdiff` finishes in `1.15 s`.
  - **Protobuf streaming changes under `--breaking wire` ([#153](https://github.com/noemaforge/vimanam/issues/153))**: `RPC_SAME_CLIENT_STREAMING` and `RPC_SAME_SERVER_STREAMING` fail default `--breaking all` and `--breaking source`, but are not yet classified under `--breaking wire`.
  - **Inline OpenAPI request schema `request.` prefix ([#156](https://github.com/noemaforge/vimanam/issues/156))**: inline request bodies prefix fields with `request.` in Markdown tables, which caused LLMs in the eval to echo prefixed field names on `oa_batches` and `oa_stripe_payment_intents`.
  - **Mixed `protoc` `.pb` vs `v2.2.0` `.proto` diffs ([#155](https://github.com/noemaforge/vimanam/issues/155))**: comparing a prebuilt `.pb` from a newer `protoc` against a `.proto` compiled by `v2.2.0` can report deltas inside `google/protobuf/descriptor.proto` when imported transitively.
  - **Protobuf Editions ([#157](https://github.com/noemaforge/vimanam/issues/157))**: Vimanam supports proto2 and proto3 and rejects Protobuf Editions until `prost-reflect` adds safe Editions feature decoding.
  - **Parser speed vs memory and binary size**: on Stripe `6.3 MB` YAML, `serde-saphyr` is `+13.1 ms` (`+6.8%`) slower by median than `serde_norway` while cutting peak RAM by `19.8%` and eliminating `unsafe-libyaml-norway` (`#![forbid(unsafe_code)]` lives on `serde-saphyr`, not crate-wide on `vimanam/src/`). On GitHub `1.2 MB` GraphQL SDL, `apollo-parser` adds `+12.1 ms` (`+22.9%`) for lossless CST parsing. The `arm64` release binary grew from `7.24 MB` to `9.28 MB` (`+2.04 MB`).
</Aside>

## Reproduce these measurements

Run the checked-in benchmark and evaluation scripts, or invoke `hyperfine` directly (using `--env PATH=` with an absolute binary path so `hyperfine` remains discoverable while `vimanam` executes with an empty `PATH`):

```bash
# 1. Pure-Rust .proto compilation verified with empty PATH
VIMANAM="$(command -v vimanam)"
git clone --depth 15 https://github.com/open-telemetry/opentelemetry-proto.git
hyperfine --env PATH= --warmup 2 --runs 10 \
  "'$VIMANAM' opentelemetry-proto/opentelemetry/proto/collector/trace/v1/trace_service.proto -I opentelemetry-proto --detail full --include-schemas --no-report"

# 2. Full public benchmark, BPE calibration, 200-proto Git-ref scaling, and 4 external baselines
uv run --with tiktoken python3 scripts/benchmark-public.py \
  --v21 /path/to/vimanam-2.1.0 \
  --v22 /path/to/vimanam-2.2.0 \
  --corpus /tmp/vimanam-eval-corpus \
  --runs 10 \
  --output scripts/benchmark-v22-results.json

# 3. 3-trial end-to-end routed + oracle LLM evaluation (Claude API vs o200k_base calibration)
uv run --with tiktoken python3 scripts/eval-context-accuracy.py \
  --v22 /path/to/vimanam-2.2.0 \
  --corpus /tmp/vimanam-eval-corpus \
  --model haiku \
  --trials 3 \
  --workers 3 \
  --output scripts/eval-context-accuracy-results.json
```
