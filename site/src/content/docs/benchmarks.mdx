## Task-accuracy evaluation: raw spec vs summary vs focused slice

Extracting one operation out of 612 is selection, not compression. The real question is whether an LLM given a focused Vimanam slice answers exact contract questions as accurately as one given the raw specification — and what happens when a raw spec overflows the context window.

### Experimental setup

Ten contract tasks across OpenAI OpenAPI 3.0 (`1.3 MB` YAML), Stripe OpenAPI 3.0 (`7.9 MB` JSON), gRPC Health (`health-v1.20.0.proto`), OpenTelemetry Collector (`trace_service.proto` and `metrics_service.proto` with transitive imports), SpaceX Land GraphQL (`12 KB` SDL), and GitHub GraphQL (`1.2 MB` SDL) ran under four conditions on the same model (`claude-haiku-5-5`, zero tools, isolated system prompt):

1. **`no_spec`** *(memorization control)*: question only, no contract context.
2. **`summary`**: `vimanam --detail summary --no-report`.
3. **`raw_spec`**: raw YAML, JSON, concatenated `.proto` + transitive imports, or raw `.graphql` SDL.
4. **`focused_slice`**: single-turn `vimanam --operation ... --detail full --include-schemas --schema-depth 2` (or depth `3` for nested OTel RPCs; plus `--schema` for GraphQL input objects).

Every response was graded programmatically on strict JSON assertions (`50` assertions across `10` tasks; no LLM judge).

What the raw results show honestly:

1. **Cost and context-window survival**: on the 8 tasks where `raw_spec` fit in context, `raw_spec` spent **`$1.7119`** (`1.74M` API input tokens) versus **`$0.0074`** (`26.3k` API input tokens) for `focused_slice` — **231× lower cost** (`120×` lower across all 10 tasks). On both Stripe `7.9 MB` tasks (`1.42M` `o200k_base` tokens), `raw_spec` exceeded the 1M-token window completely while `focused_slice` passed **`4/4`** on both (`$0.0016` and `$0.0053`).
2. **Note 1 — two strict-string mismatches on OpenAI (`oa_batches` 4/5, `oa_files` 3/4)**: inspecting the model's exact responses showed every fact was present in the Markdown slice. On `oa_batches`, the model returned `["request.input_file_id", "request.endpoint", "request.completion_window"]` (copying the `request.` prefix from Vimanam's Request Schema table); on `oa_files`, it returned `"OpenAIFile object with fields: ..."` instead of bare `"OpenAIFile"`.
3. **Note 2 — `--schema-depth 3` truncation on OTel (`pb_otel_trace` 3/7, `pb_otel_metrics` 3/5)**: at `--schema-depth 3`, Vimanam stopped before `ExportTracePartialSuccess` and `ExportMetricsPartialSuccess` and printed the exact `--schema` retrieval command. Because the single-turn harness gave the model no tools, it declined to guess the omitted fields (even though it recalled them from training data under `no_spec`!). Appending Vimanam's printed `--schema` follow-up command lifted `pb_otel_trace` to **`7/7`** (`1,785` BPE tokens) and `pb_otel_metrics` to **`5/5`** (`1,769` BPE tokens).
4. **Why `summary` is a router, not a payload reference**: `--detail summary` scored `25/50` assertions (mostly `operationId` plus memorized OTel/gRPC Health facts) and `0/5` on both GraphQL tasks. Use `summary` or `SKILL.md` to pick an operation, then load the focused slice.

## Standalone v2.2.0 performance and BPE tokenization

### Exact `o200k_base` BPE tokens vs `chars / 4` estimate

Vimanam's `--max-tokens`, `--stats`, and `--costs` use a fast `chars / 4` heuristic (`estimate_tokens` in `src/markdown/mod.rs`). Because JSON, YAML, GraphQL SDL, `.proto`, and Markdown tables tokenize differently, the table below compares exact `tiktoken` (`o200k_base`) BPE token counts against `chars / 4`:

| Public specification | Raw `o200k_base` BPE | Raw `chars / 4` (chars/BPE) | Full Markdown `o200k_base` BPE | Full MD `chars / 4` (chars/BPE) | Focused slice `o200k_base` BPE | Selection ratio (BPE) |
|---|---:|---:|---:|---:|---:|---:|
| **Stripe OpenAPI 3.0** (`7.9 MB` JSON) | `1,418,244` | `2,079,211` (`5.86`) | `1,095,911` | `1,147,353` (`4.19`) | `3,693` (`POST /v1/customers`) | `99.7%` fewer |
| **OpenAI OpenAPI 3.0** (`1.3 MB` YAML) | `281,146` | `343,997` (`4.89`) | `151,987` | `154,266` (`4.06`) | `1,286` (`POST /chat/completions`) | `99.5%` fewer |
| **GitHub GraphQL API** (`1.2 MB` SDL) | `286,673` | `305,959` (`4.27`) | `414,860` | `427,790` (`4.12`) | `9,902` (`Query.repository`) | `96.5%` fewer |
| **SpaceX Land GraphQL** (`12 KB` SDL) | `3,672` | `3,110` (`3.39`) | `15,129` | `13,556` (`3.58`) | `510` (`Query.launchesPastResult`) | `86.1%` fewer |
| **OTel TraceService** (4 `.proto` files) | `6,696` | `7,036` (`4.20`) | `9,369` | `9,359` (`4.00`) | `1,393` (`TraceService.Export`, d=3) | `79.2%` fewer |

Calibration takeaways:

- **On Vimanam's rendered Markdown**, `chars / 4` tracks `o200k_base` closely (`4.00–4.19` chars/BPE, within `±5%` on large specs; `3.58` on small dense GraphQL tables).
- **On raw JSON and YAML**, `chars / 4` overestimates real BPE tokens by `22%–47%` (`4.89` chars/BPE on OpenAI YAML, `5.86` on Stripe JSON) because repeated indentation merges into single BPE tokens.
- **Full-document Markdown vs raw source**: for verbose OpenAPI JSON/YAML, full Markdown is smaller than the raw spec (`-23%` to `-46%` BPE). For terse GraphQL SDL and `.proto`, full Markdown with tables is larger than raw source — focused selection (`--operation`, `--schema`, `--output-mode skill`) is what reduces context size.

## External baseline comparisons: `oasdiff` and `buf breaking`

Diff correctness matters more than diff speed. Both comparisons below run against installed release binaries on the same machine (`oasdiff 1.39.0` and `buf 1.75.0`).

### OpenAPI: `vimanam diff` vs `oasdiff 1.39.0`

Tested across a 6-case OpenAPI 3.0 mutation matrix (`--fail-on-breaking` vs `oasdiff breaking --fail-on ERR`) and `tests/fixtures/diff_old_oas3.json -> diff_new_oas3.json`:

| OpenAPI mutation case | `vimanam diff` (v2.2.0) | `oasdiff breaking` (1.39.0) | Notes |
|---|---|---|---|
| Endpoint removed (`POST /v1/items`) | Breaking (`operation_removed`) | Breaking (`api-removed-without-deprecation`) | Exact agreement |
| Required query parameter added | Breaking (`argument_added`) | Breaking (`new-required-request-parameter`) | Exact agreement |
| Request body property made required | Breaking (`field_required_changed`) | Breaking (`request-property-became-required`) | Exact agreement |
| Optional response property removed | **Breaking** (`field_removed`) | **Non-breaking** *(not ERR)* | `oasdiff` flags required-property removals as ERR and optional ones as WARN; Vimanam treats any response field removal as breaking |
| Optional response property added | Non-breaking (`field_added`) | Non-breaking | Exact agreement |
| Versioned path moved (`/v1/items -> /v2/items`) | Breaking (`operation_moved`) | Breaking (`api-path-removed-without-deprecation`) | Vimanam pairs the move and attributes inner changes; `oasdiff` reports separate path removal |

- **Timing on `diff_old_oas3.json -> diff_new_oas3.json` (10 runs)**: `vimanam` `12.68 ± 3.79 ms` (`5.2 MB` RSS, `57.0M` instructions) vs `oasdiff` `16.67 ± 2.13 ms` (`24.1 MB` RSS, `123.3M` instructions — wall-time difference is within `1σ` noise; Vimanam uses `4.6×` less memory).
- **Known scope difference**: `vimanam diff` compares the first request/response media type only; `oasdiff` checks every media type in `content`.

### Protobuf: `vimanam diff` vs `buf breaking 1.75.0`

Tested across an 8-case proto3 compatibility matrix comparing `vimanam --breaking wire` against `buf` `WIRE`, and `vimanam --breaking source` against `buf` `WIRE_JSON` and `FILE`:

| Protobuf mutation case | Vimanam `wire` / `buf WIRE` | Vimanam `source` / `buf FILE` | Native rule names |
|---|---|---|---|
| Field type changed (`int32 -> string`) | Breaking / Breaking | Breaking / Breaking | `FIELD_SAME_TYPE` (match) |
| Field removed without reserving number | Breaking / Breaking | Breaking / Breaking | `FIELD_NO_DELETE*` (match) |
| Field removed with `reserved 2` | Pass / Pass | Breaking / Breaking | `FIELD_NO_DELETE` (match) |
| Same-number field rename (`quantity -> qty`) | Pass / Pass | Breaking / Breaking | `FIELD_SAME_NAME`, `FIELD_SAME_JSON_NAME` (match) |
| `json_name` override changed | Pass / Pass | Breaking / Breaking | `FIELD_SAME_JSON_NAME` (match) |
| Enum value removed without reserving number | Breaking / Breaking | Breaking / Breaking | `ENUM_VALUE_NO_DELETE*` (match) |
| RPC changed unary → server streaming | **Pass** / **Breaking** | Breaking / Breaking | `RPC_SAME_SERVER_STREAMING` *(wire divergence — see below)* |
| Optional field added | Pass / Pass | Pass / Pass | Non-breaking (match) |

Two genuine policy differences surfaced by the comparison:

- **`RPC_SAME_SERVER_STREAMING` under `--breaking wire`**: `buf` `WIRE` flags changing an RPC from unary to server streaming as wire-breaking; `vimanam 2.2.0` classifies it under `source` (and default `--breaking all`), not `--breaking wire`.
- **File options on `grpc/grpc` `health-v1.0.0 -> v1.20.0`**: `buf` `FILE` flags newly added `go_package`/`java_*` file options as breaking (`exit 100`), whereas `vimanam` classifies file-option additions as `review`.
- **Timing on `health-v1.0.0 -> v1.20.0` (10 runs)**: `vimanam` **`10.33 ± 2.35 ms`** (`6.2 MB` RSS, `39.2M` instructions, no `buf.yaml`) vs `buf breaking` **`39.67 ± 4.46 ms`** (`49.4 MB` RSS, `434.8M` instructions — `3.84×` faster, `7.9×` less memory).

## Upgrade analysis: v2.2.0 vs v2.1.0

Vimanam `2.2.0` dropped two external/unsafe runtime dependencies — replacing external `protoc` with pure-Rust `protox 0.10`, replacing `serde_norway` (which wraps C-ported `unsafe-libyaml-norway`) with `serde-saphyr 2.2` (whose crate declares `#![forbid(unsafe_code)]`), replacing unmaintained `graphql-parser 0.4` with `apollo-parser 0.8`, displaying `.proto` source comments, and fixing `RUSTSEC-2026-0486`.

### Protocol Buffers: 6.0x–7.4x faster `.proto` compilation and 31x faster 200-proto Git diffs

Eliminating `protoc` subprocess spawns cuts compile-and-render wall time well outside `1σ` noise while running with an empty `PATH`:

## Trade-offs and known limits

<Aside type="caution" title="Measured trade-offs in v2.2.0">
  - **Binary size**: the `arm64` release binary grew from `7.24 MB` to `9.28 MB` (`+2.04 MB`) to bundle `protox`, Google well-known descriptors, `apollo-parser`, `serde-saphyr`, and optional Nushell/manpage crates.
  - **GraphQL SDL parse time**: `apollo-parser`'s lossless CST costs `+10.6 ms` on GitHub's `1.2 MB` SDL (`53.1 -> 63.7 ms`, `+42%` CPU instructions) in exchange for `extend schema`, `@oneOf`, repeatable directives, and stricter syntax validation.
  - **Mixed `protoc` `.pb` vs `v2.2.0` `.proto` diffs**: source-to-source diffs under `v2.2.0` are deterministic across machines because `protox` pins one bundled `google/protobuf/descriptor.proto`. Comparing a prebuilt `.pb` from a newer `protoc` directly against a `.proto` compiled by `v2.2.0` can report deltas inside `google.protobuf.descriptor.proto` when imported transitively.
  - **YAML `unsafe` scope**: `#![forbid(unsafe_code)]` is declared by the `serde-saphyr` dependency (replacing `serde_norway`'s C-ported `unsafe-libyaml-norway`), not as a crate-wide attribute on `vimanam/src/`.
</Aside>

## Reproduce these measurements

Run the full checked-in benchmark and accuracy scripts, or invoke `hyperfine` directly (using `--env PATH=` with an absolute binary path so `hyperfine` itself remains discoverable while `vimanam` executes with an empty `PATH`):

```bash
# 1. Pure-Rust .proto compilation verified with empty PATH
VIMANAM="$(command -v vimanam)"
git clone --depth 15 https://github.com/open-telemetry/opentelemetry-proto.git
hyperfine --env PATH= --warmup 2 --runs 10 \
  "'$VIMANAM' opentelemetry-proto/opentelemetry/proto/collector/trace/v1/trace_service.proto -I opentelemetry-proto --detail full --include-schemas --no-report"

# 2. Full public benchmark, BPE calibration, 200-proto Git-ref scaling, and oasdiff/buf baselines
uv run --with tiktoken python3 scripts/benchmark-public.py \
  --v21 /path/to/vimanam-2.1.0 \
  --v22 /path/to/vimanam-2.2.0 \
  --corpus /tmp/vimanam-eval-corpus \
  --runs 10 \
  --output scripts/benchmark-v22-results.json

# 3. 10-task LLM context-accuracy evaluation
uv run --with tiktoken python3 scripts/eval-context-accuracy.py \
  --v22 /path/to/vimanam-2.2.0 \
  --corpus /tmp/vimanam-eval-corpus \
  --model haiku \
  --output scripts/eval-context-accuracy-results.json
```
